# results/ 归档约定

## 命名

| 类型 | 文件名 | 统计 | 入库 |
|---|---|---|---|
| 正式结果 | `result-YYYYmmdd-HHMMSS.json` | **计入成绩** | 是（`results/` 只留最新一份） |
| 作废结果 | `result-INVALID-<原因>-YYYYmmdd-HHMMSS.json` | **永不计入** | **是**（事故留档＝治理证据） |
| 历史正式结果 | 原名不变 | 不计入当前成绩 | 否（`results/archive/`，随时可重跑） |

文件名里带 `-INVALID-` 即作废，任何汇总/对比脚本都要先排除它。

## 什么情况标 INVALID

- **题集不对**：跑的不是 `tasks.json` 里的设计题（例如跑了自己另出的题）——原因写 `自行出题`
- **中途改过判据/工具**：同一轮里评测逻辑和金标不是同一套
- **跑挂了**：异常导致结果不完整

**作废也入库**：`result-INVALID-*` 是治理证据，不是垃圾。它能回答三个别的
东西回答不了的问题——这份成绩为什么不作数、当时错在哪、同样的错怎么避免复发。
删掉它，三个月后只剩一个孤零零的 `100%`，没人记得那 100% 是通过了自己的题。
（这也是 `.gitignore` 里唯独放行 INVALID、却忽略 `archive/` 的原因：前者不可
再生，后者随时能重跑。）

## 自动归档

`run_eval.py` 每次写出新结果后，会把 `results/` 里更早的正式结果自动移进
`results/archive/`（INVALID 的不动，就留在原地当警示）。所以 `results/` 里
`result-*.json` 只有一份 = 最近一次正式跑。

- `result-INVALID-自行出题-20260929-173057.json`
- `result-INVALID-自行出题-20260929-174406.json`

这两份是拿**自行设计的 10 题**（T01-T10）跑的，不是 `tasks.json` 的设计题
（t01-…~t10-…）。当时报出的 100% 是「通过了自己的题」，不作数。以设计题跑的
结果才有效。

教训（下次别犯）：**任务集是别人的设计基准时，一个字符都不许改**；觉得设计
能改进，提建议、不动手。判据和题集一改，前后两轮成绩就不可比——v1 的 80% 和
v2 的 100% 也是同理，不是模型变强了，是题面和判据变了。
