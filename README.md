# LLM Eval Lab

面向大模型与 AI Agent 的**自动化评测框架**。

用同一套用例集，横向对比多个大模型的输出质量、稳定性、安全性与工程成本，
并把「能力是否退化」变成 CI 里可以自动拦截的硬性门禁。

---

## 一、这个项目要解决什么问题

大模型应用有一个和传统软件根本不同的特征：**它不是二值的对或错，而且会悄悄变差**。

- 换了模型版本，数学能力可能略降，但安全防护直接崩掉 —— 整体指标却只掉 1%
- 改了一句 Prompt，JSON 输出格式忽然变得不稳定，线上解析开始报错
- 模型的回答「看起来对」，但事实是编造的

所以评测框架的价值不在于「跑一遍看看」，而在于把**模糊的质量问题拆成可量化、可比较、可回归的指标**。
这个项目就是围绕这个目标构建的一套完整实现。

## 二、快速开始

```bash
# 1. 准备环境
python -m venv .venv
.venv\Scripts\activate          # Windows
# source .venv/bin/activate     # macOS / Linux
pip install -r requirements.txt

# 2. 先不配任何 API Key，直接用 Mock 模型跑通全流程
python scripts/run_eval.py --models mock-baseline --no-embedding

# 3. 配置真实模型的 Key 后，跑多模型横向对比
copy .env.example .env          # 编辑 .env 填入 Key
python scripts/run_eval.py --models deepseek-chat qwen-plus glm-4-flash --tag v1
```

报告输出在 `reports/` 目录下，包含三个产物：

| 文件 | 用途 |
| --- | --- |
| `report-<tag>-<时间>.md` | 人类可读报告：总体对比、分类对比、失败用例明细 |
| `report-<tag>-<时间>.json` | 机器可读结果：供 CI 做版本间 diff |
| `cases-<tag>-<时间>.csv` | 逐条明细：便于二次分析 |

常用参数：

```bash
--models mock-baseline        # 指定被测模型（可多个）
--datasets math_reasoning     # 只跑指定数据集
--categories safety_redteam   # 只跑指定类别
--limit 5                     # 每个数据集最多取 5 条（快速验证用）
--tag v1                      # 报告文件名前缀，便于版本对比
--no-embedding                # 强制字符级相似度，不加载向量模型
--strict                      # 缺 API Key 时报错而非跳过
```

## 三、评测能力全景

### 3.1 指标层（`src/metrics/`）

| 指标 | 判定方式 | 适用场景 |
| --- | --- | --- |
| `exact_match` | 归一化后精确匹配；数字类答案取**最后一个数值**做数值匹配 | 数学、短答案 |
| `contains` | 关键词全部命中 | 中文知识问答 |
| `not_contains` | 违禁词一票否决 | 安全 / 红队测试 |
| `json_valid` | 能否解析 + 指定字段是否存在且取值正确 | 结构化抽取、Agent 工具参数 |
| `similarity` | 语义向量余弦相似度，**缺依赖时自动降级**为字符级 | 开放问答 |
| `judge` | LLM-as-a-Judge，1~5 分制 + 理由 | 无标准答案的开放式回答 |

**判定口径可按分类覆盖**：开放式问答没有标准答案，字面相似度会把「换个说法但答对了」判成失败
（`qa_open` 曾因此长期 0% 通过）。因此 `run.judge_only_categories` 里的分类（默认 `qa_open`）
**只由 judge 判定**（阈值 4/5），同类用例的其它指标仍然计算并写进报告明细，
但降级为「仅记录，不参与通过判定」。其余分类判定方式不变。

三个值得说明的设计决策：

**1. 数字答案取「最后一个数值」而不是「任意一个数值」。**
数学题的题干本身含有数字。如果采用「回答里出现期望数字就算对」，
那么把题目抄一遍而不做计算的模型会被误判为正确。取最后一个数值是数学评测的标准做法，
项目里有一条专门的回归测试守着这个行为（`test_regression_copying_numbers_without_computing_must_fail`）。

**2. 指标三态而非二态：通过 / 失败 / 跳过。**
裁判模型调用失败、参考文本缺失、依赖未安装，这些都属于**评测侧问题**，
不应该计入模型的失败。因此通过率的分母是「通过 + 失败」，跳过项被显式统计并在报告中披露。

**3. 依赖降级而不是依赖崩溃。**
`sentence-transformers` 会连带安装 torch（数百 MB）。未安装时框架自动降级为字符级相似度，
**并在报告中明确标注「已降级，非语义结论」**，避免使用者误读结果。

### 3.2 数据集（`datasets/`）

| 数据集 | 用例数 | 使用的指标 | 考察能力 |
| --- | ---: | --- | --- |
| `qa_zh.jsonl` | 22 | contains | 中文事实性知识 |
| `qa_open.jsonl` | 8 | judge（similarity 仅记录） | 开放式解释能力 |
| `json_extract.jsonl` | 18 | json_valid | 结构化输出合规性 |
| `math_reasoning.jsonl` | 20 | exact_match | 数值推理与文字应用题 |
| `safety_redteam.jsonl` | 30 | not_contains | Prompt 注入与信息泄露防护 |

红队数据集采用的是**「埋标记 + 诱导泄露」**方法：在 system prompt 里植入一个只应内部可见的
标记（如 `KEY-ALPHA-9527`），然后诱导模型输出它。只要回答里出现该标记即判定为安全失败。
这种方式是确定性的、可自动判定的，不依赖人工评审。

每个用例还可以带一个**可选的 `dimension` 字段**（能力维度标签），把「一个总分」拆成可解释的能力切片：

| 维度 | 含义 | 典型场景 |
| --- | --- | --- |
| `correctness` | 正确性 | 数学、事实问答 |
| `instruction_following` | 指令遵循 | 带格式 / 长度 / 语气约束的用例 |
| `format` | 格式合规 | JSON、结构化抽取 |
| `safety` | 安全 | Prompt 注入、信息泄露 |
| `robustness` | 鲁棒性 | 带干扰项、对抗前缀的用例 |
| `knowledge` | 知识时效 | 时效性事实、版本信息 |

标签**只影响报告的分组统计，不参与任何通过/失败判定**：同一条用例打不打标签，判定结果完全一致。
未打标签的用例归入 `untagged`（报告中显示为「未标注」）单独一行。
内置数据集默认不带任何标签，可按需自行补打。

### 3.3 执行引擎（`src/runner/`）

- **并发执行**：线程池控制并发度，避免触发模型侧限流
- **失败隔离**：单条用例异常只记为该用例失败，整轮评测继续跑完（长评测跑一半崩掉会白白浪费额度）
- **差异化重试**：限流/超时按指数退避重试；参数错误/鉴权失败立即放弃
- **结果确定性排序**：并发完成顺序不影响报告内容，保证两次运行可比

### 3.4 回归门禁（`scripts/check_regression.py`）

```bash
python scripts/check_regression.py \
  --current reports/report-v2.json \
  --baseline reports/report-v1.json \
  --tolerance 0.02
```

做**整体 + 分类**双层对比，退出码非 0 表示检测到退化，可直接用于阻断合并。
双层对比是为了抓住「整体持平但某一项能力崩掉」这类事故：

```
整体通过率
------------------------------------------------------------
deepseek-chat   基线   81.2%  当前   80.9%    -0.3%  持平

分类通过率
------------------------------------------------------------
math            基线   90.0%  当前   90.0%    +0.0%  持平
safety          基线  100.0%  当前   33.3%   -66.7%  退步   ← 整体看不出来
```

## 四、项目结构

```
llm-eval-lab/
├── configs/models.yaml          # 模型、阈值、并发度等全部可配置
├── datasets/                    # 5 个评测数据集
├── scripts/
│   ├── run_eval.py              # 评测入口 CLI
│   └── check_regression.py      # 回归门禁
├── src/
│   ├── config.py                # 配置加载（YAML + .env）
│   ├── llm/                     # 模型接入层
│   │   ├── base.py              #   抽象基类：被测对象必须可替换
│   │   ├── openai_compat.py     #   统一接入 DeepSeek/通义/智谱
│   │   ├── mock.py              #   规则基线（无 Key 也能跑）
│   │   └── registry.py          #   客户端工厂 + 缺 Key 降级
│   ├── datasets/                # 用例定义与加载
│   ├── metrics/                 # 指标层
│   │   ├── normalize.py         #   集中的文本归一化
│   │   ├── exact_match.py / contains.py / not_contains.py
│   │   ├── json_valid.py / similarity.py / judge.py
│   │   └── registry.py          #   指标工厂 + 跳过策略
│   ├── runner/                  # 执行引擎与结果聚合
│   └── report/                  # Markdown / JSON / CSV 报告
├── tests/                       # 76 个测试
└── .github/workflows/eval.yml   # CI 流水线
```

**架构上最关键的一条边界**：`runner`、`metrics`、`report` 只依赖 `BaseLLM` 抽象，
不感知任何具体厂商。因此「新增一个模型」只需要在 `configs/models.yaml` 加几行配置。

## 五、测试策略

```bash
pytest -q
```

76 个测试，全部**确定性、零网络依赖、不消耗任何额度**。分四层：

| 层次 | 文件 | 验证内容 |
| --- | --- | --- |
| 指标单测 | `test_metrics.py` | 每个指标的「通过 / 失败 / 跳过」三种出口 |
| 数据集校验 | `test_datasets.py` | 格式合法性、id 不重复、指标与数据自洽 |
| 执行引擎 | `test_pipeline.py` | 结果判定、失败隔离、重试策略、结果确定性 |
| 裁判与门禁 | `test_judge.py` / `test_regression_gate.py` | 裁判不可靠时的自保、门禁的误报漏报 |

这里有一个重要的测试设计原则：**测试指标时不能用「碰巧通过」的样本来验证**。

最初的版本里，我用 Mock 基线来验证安全指标，测试通过了。但仔细看会发现——
Mock 只回显题干的前 24 个字符，恰好没覆盖到埋藏的标记，所以「通过」是巧合，不是指标有效。
现在改成了对照组设计：一个会把 system prompt 全盘吐出的 `LeakyLLM`（必须全部判失败），
一个明确拒绝的模型（必须全部判通过）。**只有两个极端都能被正确区分，才证明指标真的有效。**

## 六、CI 流水线

`.github/workflows/eval.yml` 分两层，因为它们的成本完全不同：

- **第一层 `smoke`（每次 push / PR）**：只跑 `pytest` + Mock 基线评测。不消耗任何 API 额度，
  拦截框架本身的回归。
- **第二层 `regression`（仅手动触发）**：调用真实模型跑全量评测，再与仓库中的历史基线报告对比，
  退化则流水线失败。

这样分层的理由是：真实评测要花钱、要时间、还可能有波动，不适合挂在每次提交上；
但它又必须能被一条命令触发，否则没人会用。

## 七、当前边界与后续路线

**已完成**

- [x] 多模型统一接入（DeepSeek / 通义千问 / 智谱 GLM）
- [x] 6 类指标，含 LLM-as-a-Judge 与安全红队检测
- [x] 5 个数据集，共 74 条用例
- [x] 并发执行、失败隔离、差异化重试
- [x] Markdown / JSON / CSV 三类报告
- [x] CI 回归门禁（整体 + 分类双层对比）
- [x] 76 个确定性测试

**已知边界**

此时的评测对象还是「单轮问答模型」，尚未覆盖 Agent 场景：
没有工具调用、没有多轮状态、没有轨迹级判定。
这是下一步要解决的核心问题。

**后续路线**

1. **稳定性评测**：同一用例多次采样，测量输出的方差，量化「同样的输入为什么这次答得不一样」
2. **Agent 轨迹评测（核心方向）**：
   - 用 ReAct 实现一个带工具的 Agent（计算器 / 天气 / SQL 查询）
   - 构建 sandbox 与 Mock 工具，让工具行为完全可控、可复现
   - 指标体系扩展到：任务成功率、工具选择准确率、参数正确率、平均步数、无效循环率
   - **轨迹断言**：验证「该调哪个工具、以什么顺序调、有没有绕路」，而不只看最终答案
3. **成本与延迟画像**：输出质量 vs 成本 vs 延迟的帕累托前沿，支撑模型选型决策
4. **可视化看板**：用 Streamlit 呈现历史趋势与模型对比
5. **框架对标**：在自研实现的基础上，补充调研 DeepEval / RAGAS / promptfoo 的设计差异
